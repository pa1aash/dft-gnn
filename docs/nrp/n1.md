# N1: GPU repeatability of the sweep (2026-10-10, interim)

**Status:** 48 runs complete on 3 GPU classes and 4 nodes. The A10 same-node repeat (pass 2 on `gpu-05`) is
running and will be added. RTX 4090 and L4 have no runs: no GPU of either class was free on the nodes this
namespace can use during the session. The comparison is descriptive only (`results/nrp/nrp_n1_gpu_repeat.json`,
`scripts/nrp/n1_compare.py`); no tests or thresholds are applied.

## What was run

The 12 primary-sweep specs at resample 0, unchanged from the sweep stage builder: models S and D-state, budgets
B = 654 and 200 training hosts, seeds 0-2, tuned-v1 hyperparameters, max_epochs 200, patience 30. They were run
sequentially, one training process per GPU, on each GPU class (`scripts/nrp/n1_run.py`, Jobs from
`scripts/nrp/n1_launch.sh`, pod setup in `scripts/nrp/n1_pod.sh`). Every record carries the GPU model, UUID,
driver, CUDA, node and pod hostname, torch and matgl versions, the torch determinism flags, wall time and peak GPU
memory, and was written with `write_result` from a clean tree.

| NVIDIA A10 | gpu-18.nrp.mghpcc.org | 12 | 615.71.09 | 2.7 h |

Software on every node: torch 2.13.0+cu130 (CUDA 13.0), matgl 4.1.0, environment `env/lock-nrp-rtx2080ti.txt`
from N0. The determinism flags in effect were `use_deterministic_algorithms=True` with `warn_only=True`, cuDNN
benchmark off. Peak GPU memory was at most 4.65 GB, so the A4000 ran every spec without running out of memory.
No run used either excluded node: `hcc-nrp-shor-c6017.unl.edu` (CUDA illegal-address errors, 2026-10-08) or
`nautilus-ext-gpu01.fullerton.edu` (an RTX 3090 that raised CUDA unknown error when the model was moved to the
GPU, for every run, on 2026-10-10; that attempt wrote no records).

## Findings

**Same GPU model, different node: identical.** All 12 A10 runs on `gpu-18` produced predictions bitwise identical
to those on `gpu-05`. The first pass-2 run on `gpu-05` (S, B = 654, seed 0, on a different physical A10 of that
node) is also bitwise identical to pass 1. With this software stack, training is deterministic for a given GPU model
and driver.

**Different GPU model: different trajectories.** No run on any class reproduces the original sweep's predictions
bitwise, and the classes differ from each other. The per-site prediction differences are not small for individual
runs (largest absolute difference per class 3.1 to 3.9 eV, mean absolute difference 0.10 to 0.75 eV per run),
because a different floating-point summation order changes the training trajectory and therefore the early-stopping
epoch. The single-run test MAE moved by -0.05 to +0.24 eV against the original run.

**Seed-ensemble MAE** (the primary-analysis prediction, the mean of three seeds per site), minus the original
sweep's, in eV, with the seed SD of MAE at the same (model, B) from `results/g1_variance.json` for scale:

| Model, B | A10 (both nodes) | RTX 3090 | RTX A4000 | Seed SD |
|---|---|---|---|---|
| S, 654 | -0.013 | -0.017 | -0.002 | 0.048 |
| S, 200 | +0.021 | +0.029 | +0.102 | 0.049 |
| D-state, 654 | -0.005 | -0.022 | +0.000 | 0.020 |
| D-state, 200 | +0.004 | -0.000 | +0.009 | 0.025 |

Ten of the twelve differences are smaller than the seed SD. The two that are larger are the A4000 at S, B = 200
(about twice the seed SD) and the RTX 3090 at D-state, B = 654 (just above it).

## How to read this against the original sweep

The original sweep (code `f943fdff`) did not record its GPU model; its records carry only `device: cuda` and the
container hostname `95ff7c91c41f`. The differences against it therefore mix GPU model with any difference in
environment, and cannot be attributed to either. The training code that these specs exercise is unchanged between
`f943fdff` and the N1 base `e6d1a84`: the changes in `dftgnn.train` and `dftgnn.models` add new models, splits and
options that these specs do not use. The within-N1 comparisons (same class across nodes, same node across passes,
class against class) all use one commit and one environment.
